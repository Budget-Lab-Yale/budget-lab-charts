# budget-lab-charts

The Budget Lab's published-figures archive: chart/table specs and data, built and published by CI.
The chart engine is a pinned dependency (`budget-lab-chart-engine`); this repo is content plus the
build, the gallery, and the embed loader. Merging to `main` publishes.

Checks: `npm run validate` (the merge gate), `npm test`.

## Hard invariants

Constraints that no single file states and that a reviewer cannot infer from a diff. **A violation of
any of these is a top-severity finding, not a nitpick.** Paste this section verbatim into code-review
prompts (see the `gpt-review` skill). Add to it when a bug or a review reveals a new one.

- **`npm run validate` is the merge gate, and the `Validate` CI job is the only required status
  check on `main`.** Anything that must not drift belongs in it as a stage rather than in prose —
  that is why the vendored engine spec and the house palette are gated there. A rule enforced only
  by documentation is not enforced: the palette rule lived in skill prose and `navy` still reached a
  figure, because prose only guides Claude and a hand-edited spec bypasses it.
- **`ENGINE-CONFIG-SPEC.md` is the pinned engine's own spec, vendored verbatim. Never edit it.**
  Re-run `npm run vendor-spec` after a repin; the drift check in `npm run validate` fails until you
  do. It is named `ENGINE-CONFIG-SPEC.md` here, not `CONFIG-SPEC.md`, and no workflow file mentions
  it — searching for the wrong name makes the gate look absent.
- **A repin re-renders every published figure at once.** An engine bump or a spec edit changes
  already-published output, so the archive is the blast radius, not just the figure in hand. Before
  merging either, establish which figures move by reading the archive's **specs** (not by regexing
  rendered output), and render the affected ones. A change believed to be visual-no-op must be
  *proven* one — byte-compare the render, as the hex→token substitution in `etr-vintages` was.
- **Identity is permanent.** Collection slugs and figure folder names become public embed URLs.
  Never rename them after merge.
- **`charts/trackers/` is untracked but NOT gitignored.** So `git add -A` or `git add .` will commit
  work-in-progress tracker figures that were never meant to ship — stage explicit paths in this
  repo. The same fact means CI's checkout does not contain that tree, so every `npm run validate`
  stage covers strictly fewer specs in CI than locally.
- **Series colors come from the categorical ramp** (`blue amber violet green red rose russet`, plus
  the `purple/pink/yellow/brown` aliases, each with a `-light` variant and eight tonal tiers).
  `navy` and `sky` are BRAND tokens and `grey`/`black` are role colors — none of them is a series
  color. Gated by `scripts/palette-lint.mjs`; a genuine exception goes in `PALETTE_EXCEPTIONS` with
  a reason. Note the engine deliberately accepts raw hex and 147 CSS keywords — `colorRefError`
  checks only that a color *resolves*, so "the engine accepts it" says nothing about house style.
  Slide renders under scripts/slides warn instead of fail for specs captured from an interactive
  tool or fetched from the archive (owner decision 2026-10-13); new data is held to the ramp.
- **The spec schema is strict — unknown fields fail the build.** Never invent a field. The
  authoritative field list is the engine's own schema; `ENGINE-CONFIG-SPEC.md` (vendored at the
  pinned version) documents it, including the waterfall color fields under "Waterfall options".
- **`catalog/index.json` is a build artifact** — gitignored and regenerated by CI before every
  publish. Never commit it; there is no stale-catalog step to satisfy.
- **Anything every published page must carry is applied in both `renderChart` and `reuseChart`.**
  Reused pages are copied from gh-pages, so a render-only injection (like `EMBED_HEAD`) never reaches
  them without an epoch bump. The no-JS fallback (`scripts/static-block.mjs`) is strip-and-insert on
  both paths for this reason, and its hiding CSS must stay inside its own head markers, never in
  `EMBED_HEAD`. It is applied last on render so a reused page stays byte-identical to the rendered
  one. `test/build-all.integration.test.mjs` asserts both, but it builds the whole archive and
  runs only under a local `npm test`, not in CI; run it before merging a change to either path.
- **`embed/v1/embed.js` goes live for every already-published embed the moment it merges.** Every
  deployed snippet points at that one URL — the gallery hardcodes it, so even a snippet copied from
  a PR preview points at production — and GitHub Pages serves it with `max-age=600`. A change
  reaches every host page within ten minutes with no snippet edit, and for the same reason a PR
  preview cannot exercise it. Verify a loader change locally or after merge, not on the preview.
  The reason this matters: `loading="lazy"` on the chart iframe was a silent archive-wide defect,
  because a non-scrolling renderer (Doppio PDF builds, card scrapers) never brings a below-fold
  iframe near the viewport. See the comment at that assignment for the measurements.
- **scripts/slides/ never reads the working tree under charts/, never writes under charts/, never
  commits, checks out, or otherwise changes the working tree or branches (it only fetches
  origin/main to read published figures), and its outputs never enter the archive.** Archived
  figures are read from origin/main with `git show`. Working files live beside the deck. Enforced
  in Node by assertOutsideArchive in scripts/slides/paths.mjs, which every script calls before it
  reads a working file (chart.yaml, its data file, source.json) or writes one; paths.test.mjs
  covers it and CI's Validate job runs it. insert-slide.ps1 enforces the same rule with
  Assert-OutsideArchive in scripts/slides/insert-checks.ps1, on the deck, its `_backups` folder,
  each image and its source.json, before any PowerPoint call; test-insert-checks.ps1 covers it
  COM-free, but it is Windows PowerShell, so CI does not run it.

## Review rules

For anyone reviewing a change here: Claude reviewers, Codex, `/code-review`.

**What failure means in this repo:** a published figure changes without anyone deciding it should;
an embed on a host page breaks or renders blank; a public URL (collection slug, figure folder name)
stops resolving; a figure ships off the house palette or with a field the engine rejects. Weight
findings by how directly they lead to one of these.

Check, on top of the invariants:
- **Blast radius.** For a repin or a spec edit, which published figures move, established from their
  specs. A change claimed to be visual-no-op needs a byte-compare, not an argument.
- **`embed/v1/embed.js`.** Any change is live on every host page within ten minutes of merge and a
  PR preview cannot exercise it. Check it against non-scrolling consumers (PDF builds, scrapers) and
  against every snippet form the gallery hands out.
- **Both build paths.** Anything every page must carry is applied in `renderChart` and `reuseChart`.
- **Staging.** No `git add -A` / `git add .`; nothing from `charts/trackers/` that was not meant to
  ship.
- **Tests that would pass if the change did nothing.**

Severity and noise:
- **Critical:** an invariant violation, or a defect that changes or breaks published output.
  **Important:** wrong or fragile behaviour in the change, a missed requirement, a test that asserts
  nothing. **Minor:** everything else, at most three per review. No style, naming, or formatting
  findings unless they hide a defect.
- Tag a defect the change did not introduce as **Pre-existing**. It does not block the change.
- Name the **class** of each bug and list every instance of it in the diff.
- Every finding needs a file:line from code you read and a concrete failure scenario. Do not infer
  behaviour from a file or function name. Mark what you could not verify as UNVERIFIED.
- A re-review covers the prior findings and the fix diff only. Do not re-report a finding already
  raised, ruled on, or deferred.

Skip: `_site/`, `dist/`, `node_modules/`, `.superpowers/`, `catalog/index.json`,
`ENGINE-CONFIG-SPEC.md` (vendored; check only that it was regenerated, never hand-edited), and the
rows of data CSVs (check headers and the spec that reads them, not the values). A change that is
only figure specs and data needs no Codex review.

Start the report with a count by severity ("1 Critical, 2 Minor"), or say "No issues found." plainly.
