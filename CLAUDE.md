# budget-lab-charts

The Budget Lab's published-figures archive: chart/table specs + data, built and published by
CI. The chart engine is a pinned dependency; this repo is content only.

- **Adding or updating content** (articles, trackers, figures, tables, tracker data): use the
  `publishing-figures` skill (`.claude/skills/publishing-figures/`). It covers the interview,
  data reshaping, and verification workflow.
- **Schema authority**: figure fields (`chart.yaml`, `table.yaml`, colors, CSV) are in
  `ENGINE-CONFIG-SPEC.md` — the pinned engine's own spec, vendored verbatim; never edit it, and
  re-run `npm run vendor-spec` after a repin (`npm run validate` gates it). This repo's own config
  (`article.yaml`, `tracker.yaml`, ids, figure numbers) is in `CONFIG-REFERENCE.md`. The spec schema
  is strict — unknown fields fail the build. Never invent fields.
- **Identity is permanent**: collection slugs and figure folder names become public embed URLs;
  never rename them after merge.
- **Verify**: `npm run validate` (merge gate: structure, engine schema, catalog build, vendored
  spec), then `npm run dev` (live preview at localhost:5173). `catalog/index.json` is a **build
  artifact** — gitignored, regenerated by CI before every publish, so a retitle needs no second
  step. Run `npm run catalog` locally only to assemble a full `_site/` via `npm run site`.
- **Chart pages link a shared engine asset** (`_site/embed/v1/engine-<version>.js`) rather than
  inlining the engine. `npm run assets` writes it and must run before `npm run thumbs`; `npm run all`
  handles the order. Asset filenames carry the engine version, so an engine repin needs no other
  change — but never delete a published version's assets by hand; `prune.mjs` handles retention.
- PRs get an automatic live preview URL from CI; merging to `main` publishes.
- **No design docs or plans in this repo.** There is no `docs/` folder and adding one back for a
  spec or an implementation plan is wrong — a `docs/superpowers/` pair describing the (already
  shipped) incremental-build pipeline sat here for weeks with 36 unchecked task boxes, telling any
  agent that found it to re-implement working infrastructure. Rationale for a change goes in the PR
  description, transient plans stay in the session scratchpad, invariants go in a comment where they
  apply, and anything that must not drift gets a gate in `npm run validate` (as the vendored engine
  spec does). See the global policy in `~/.claude/CLAUDE.md`.

## Hard invariants

Constraints that no single file states and that a reviewer cannot infer from a diff. **A violation of
any of these is a top-severity finding, not a nitpick.** Paste this section verbatim into code-review
prompts (see the `gpt-review` skill). Add to it when a bug or a review reveals a new one.

- **`npm run validate` is the merge gate, and the `Validate` CI job is the only required status
  check on `main`.** Anything that must not drift belongs in it as a stage rather than in prose —
  that is why the vendored engine spec and the house palette are gated there. A rule enforced only
  by documentation is not enforced: the palette rule lived in skill prose and `navy` still reached a
  figure, because prose only guides Claude and a hand-edited spec bypasses it.
- **`ENGINE-CONFIG-SPEC.md` is the pinned engine's own spec, vendored verbatim. Never edit it.**
  Re-run `npm run vendor-spec` after a repin; the drift check in `npm run validate` fails until you
  do. It is named `ENGINE-CONFIG-SPEC.md` here, not `CONFIG-SPEC.md`, and no workflow file mentions
  it — searching for the wrong name makes the gate look absent.
- **A repin re-renders every published figure at once.** An engine bump or a spec edit changes
  already-published output, so the archive is the blast radius, not just the figure in hand. Before
  merging either, establish which figures move by reading the archive's **specs** (not by regexing
  rendered output), and render the affected ones. A change believed to be visual-no-op must be
  *proven* one — byte-compare the render, as the hex→token substitution in `etr-vintages` was.
- **Identity is permanent.** Collection slugs and figure folder names become public embed URLs.
  Never rename them after merge.
- **`charts/trackers/` is untracked but NOT gitignored.** So `git add -A` or `git add .` will commit
  work-in-progress tracker figures that were never meant to ship — stage explicit paths in this
  repo. The same fact means CI's checkout does not contain that tree, so every `npm run validate`
  stage covers strictly fewer specs in CI than locally.
- **Series colors come from the categorical ramp** (`blue amber violet green red rose russet`, plus
  the `purple/pink/yellow/brown` aliases, each with a `-light` variant and eight tonal tiers).
  `navy` and `sky` are BRAND tokens and `grey`/`black` are role colors — none of them is a series
  color. Gated by `scripts/palette-lint.mjs`; a genuine exception goes in `PALETTE_EXCEPTIONS` with
  a reason. Note the engine deliberately accepts raw hex and 147 CSS keywords — `colorRefError`
  checks only that a color *resolves*, so "the engine accepts it" says nothing about house style.
- **The spec schema is strict — unknown fields fail the build.** Never invent a field. The
  authoritative field list is the engine's own `colorErrors`/schema, not the prose doc: three
  waterfall color fields exist in the schema and are absent from `ENGINE-CONFIG-SPEC.md` entirely,
  and the doc's `category_colors` applicability sentence contradicts the engine source.
- **`catalog/index.json` is a build artifact** — gitignored and regenerated by CI before every
  publish. Never commit it; there is no stale-catalog step to satisfy.
